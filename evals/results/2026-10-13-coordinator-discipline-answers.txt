**Why:** The worry is whether a general worker will reliably follow the project instructions. The skill answers that by pointing the worker at those instructions, not by relaying them. The handoff carries the `PROJECT_INSTRUCTIONS` path and the facts file. Copying conventions into the prompt would duplicate sources the worker can read, and the copy could drift from them. I also can't read the instructions on the worker's behalf, because the coordinator doesn't do subject-repository work.

**What the handoff contains**, following the implement-issue form in Handoffs:
- **Paths:** the entry skill, the implement-issue reference, and the CLI.
- **Source:** the source checkout and its revision.
- **Subject:** the issue URL, the target checkout, and the project instructions path.
- **Project facts:** the facts file path, plus `facts --issue ISSUE_URL` for live state. If `facts` reports a source as stale, I name that source so the worker reads it directly.
- **Base and existing work:** the base commit, plus the worktree, branch, head and publication state of any existing work.
- **Confirmed decisions and review plan:** the decisions already made, and the agreed review path from the recorded metadata. I'd settle that path with "Prepare required review" before substantial dependent implementation.
- **Authorization:** the flow's endpoint (PR review follow-up, no merge) and its limits. This handoff covers implementation, then draft publication through submit-pr in the same session. The worker must not mark the PR ready or request review.
- **Notes:** the task notes path, if one exists.
- **Return:** the PR URL, published head, check results, evidence limits and remaining work.

I would send the complete handoff in the dispatch call itself, not an empty or placeholder prompt. Review-changes comes later, in a fresh context, before the PR is marked ready.
